# 0032 Signed Build Provenance For Core Artifacts

Date: 2026-09-01

## Status

Accepted.

## Context

The Harness core release already verifies SHA-256 sidecars and exact
cross-platform asset inventory. Those checks prove that a downloaded file
matches a declared digest, but they do not establish where or how the binary
was built. GitHub artifact attestations provide a repository-associated,
signed build-provenance record for workflow artifacts.

## Decision

Every platform binary produced by the Harness core release build matrix must
have a GitHub artifact attestation generated by `actions/attest@v4` after the
binary's checksum and lifecycle smoke checks pass and before the artifact is
uploaded.

The attested subject is the platform binary only. The `.sha256` sidecar remains
a separately verified release asset and is not treated as provenance. The build
job receives only `contents: read`, `id-token: write`, and
`attestations: write`; the reusable post-merge caller forwards the two
additional permissions required by the called workflow.

This decision adopts GitHub's hosted attestation trust path. It does not claim
an independent publisher key, offline verification, SBOM coverage, or a
published release until a release workflow has run successfully on the
release-bearing commit. Consumers can verify a published binary with:

```bash
gh attestation verify ./harness-linux-x64 \
  -R vtp772002/harness-by-victoria
```

## Consequences

- A future core release has both byte-level checksum evidence and build
  provenance evidence for every platform binary.
- The release workflow needs narrowly scoped OIDC and attestation permissions.
- Attestation availability depends on GitHub's hosted service and its public
  repository eligibility; it is not an offline or independent publisher trust
  root.
- A workflow contract and local negative test prevent the action or required
  permissions from silently disappearing.

## Verification

The native owner is
`tests/release/test-harness-release-workflow-contract.sh`, invoked by
`scripts/validate-premerge.sh`. It proves the release workflow has the
required permissions and subject path, and that a temporary workflow missing
the attestation action is rejected. Hosted release-attestation verification
remains pending until this repository publishes its first own core release.
